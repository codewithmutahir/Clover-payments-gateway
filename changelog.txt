*** Clover Payment Gateway for WooCommerce Changelog ***

2026-10-26 - version 1.0.25
* Fix - Kitchen/receipt tickets showing garbage inside product names (e.g. "C| 6s8hicken" instead of "Chicken"). The previous kitchen-safe name hack inserted a zero-width non-joiner (U+200C) that thermal printers cannot render. Names are now plain printable text only.
* Fix - Strip zero-width / control characters from all Clover line item names and order notes before sync so product titles or customer notes cannot leak unprintable Unicode onto tickets.
* Note - Catalog 1/1 quantity display is still prevented by ad-hoc lines (no item.id) and omitting unitQty; do not reintroduce invisible Unicode into line names.

2026-10-21 - version 1.0.24
* Add - Setting "Automatic Kitchen Print" under WooCommerce → Settings → Payments → Clover Payments. Default ON (prints via Clover print_event API after each order). Disable it if the Clover device already auto-prints incoming orders — for example via a Clover marketplace app (DineNGo, OrderOut, etc.) or Clover's native Setup → Order Receipts auto-print. Leaving it on while another app also prints causes double kitchen tickets.
* Add - Filter clover_gateway_auto_print to override the setting per-order.
* Note - The deferred-print / auto-detect approach from 1.0.23 is removed. Clover's REST API does not expose installed apps, and third-party print apps like DineNGo use their own printing pipeline that does not update Clover's lineItem.printed flag, so no reliable auto-detection is possible.
* Fix - HPOS: print-fired meta uses WC_Order CRUD instead of update_post_meta().
* Fix - Guard against double-fire within the plugin: fire_order() checks the _clover_print_fired_order meta and skips if the plugin already printed this order.
* Note - Manual "Retry print" button on each order always fires regardless of the Automatic Kitchen Print setting.

2026-10-14 - version 1.0.22
* Add - A website order that reduces WooCommerce stock also reduces the linked Clover item by the quantity sold. Cancelling or refunding that order puts the quantity back. The change is recorded on the order line so a retry does not apply it twice. Items Clover is not tracking are left unchanged and noted on the order.

2026-10-14 - version 1.0.21
* Add - Variations such as Full Tray and Half tray auto-match the single Clover item named like the dish, and both keep that same quantity. A size-specific Clover item is still preferred when its name includes the size.
* Add - Optional stock check every 15 minutes copies Clover quantities onto linked WooCommerce products. Leave it off until the links have been reviewed.

2026-10-14 - version 1.0.20
* Fix - Clicking Link on the match table saved the Clover item, but a reload showed the old Possible Match again because the page was still rendering the dry-sync snapshot. Saved links and skips are now written back into that snapshot, and a reload checks the product meta before showing the row.

2026-10-14 - version 1.0.19
* Add - Clover Sync matches each WooCommerce variation to its own Clover item by SKU or by parent name plus attribute (for example "Biryani Large"). Variable parents stay in the list as a reminder that parent links do not set variation stock. An automatic link is withheld when two products would claim the same Clover item. Filter the match table to variations, then apply auto-links and import stock again.

2026-10-14 - version 1.0.18
* Add - WooCommerce → Clover Sync can import stock quantities from Clover onto products that already have a Clover item ID. Images, descriptions, prices, and URLs are not changed. Items with no Clover stock count are left unchanged. Variable parent products are skipped so each variation can be linked on its own.

2026-10-13 - version 1.0.17
* Fix - Card checkout was still creating two Clover orders because `/v1/charges` always auto-creates a Paid "Item 1" order, and a paid order cannot be deleted afterward. Card payments now create the same v3 order (real item names + taxes) used by COD/pickup, then pay that order with `POST /v1/orders/{orderId}/pay` so Clover flips THAT ticket to Paid. A standalone charge is used only when Clover rejects pay-for-order for a structural reason, and can be disabled with the `clover_gateway_allow_charge_fallback` filter.
* Fix - A failed card attempt that had already saved `_clover_order_id` was treated as success on retry (no charge). Checkout only short-circuits when `_clover_charge_id` exists or the WooCommerce order is already paid.
* Fix - When payment fails, delete the unpaid Clover order so the kitchen does not see an Open ticket. If the order already has a payment, or Clover cannot confirm that, the ticket is kept and the retry pays it instead of opening another.
* Fix - Clear the idempotency key after a decline so a retry with a different card is charged instead of replaying the original response.
* Fix - Persist Clover order/charge meta with WooCommerce CRUD methods so HPOS stores keep card and COD tickets from colliding.
* Add - Order note when Clover reports a balance still due after payment, and when the card had to be charged on a separate unitemized order.
* Note - COD/pickup is unchanged: one Open Clover order via `create_order_with_items()`, skipped for `clover_gateway`, no cash tender (cash is collected at pickup). Kitchen notes now include the WooCommerce payment method title so card vs pickup is obvious on the ticket.

2026-10-09 - version 1.0.16
* Fix - "External Payment" tender lookup only matched Clover's system labelKey (com.clover.tender.external_payment), but most merchant accounts never expose that as a toggle in Settings -> Payment Preferences -> Tenders; the only way to get an "External Payment" entry there is to add it as a CUSTOM tender, which has a merchant-generated id/label and no system labelKey. This meant record_external_card_payment() always failed to find it on those accounts, so the real order stayed Open and the throwaway order was kept as the fallback. get_external_payment_tender_id() now also falls back to a case-insensitive match on the tender's display label ("External Payment"), covering custom tenders created via the "Create custom tender" field. The custom tender label is filterable via `clover_gateway_external_payment_tender_label` in case a merchant names it differently.
* Add - `get_merchant_tenders()` (cached per-request) and `get_tender_id_by_label()` in Clover_API.

2026-10-09 - version 1.0.15
* Fix - Root cause of the duplicate-order bug, for real this time: Clover's eCommerce `/v1/charges` endpoint ALWAYS auto-creates its own order for every charge (order_id in the request body does not link to an existing order), AND Clover auto-locks an order the instant it's paid — so the 1.0.13/1.0.14 approach of charging first and editing the auto-created order afterward could never work; the edit calls were silently rejected by the lock. Reworked the flow to create the real v3 order with proper line items FIRST, charge the card via the eCommerce API separately, then record that charge as an external payment directly on the real order via `POST /orders/{orderId}/payments` with the `com.clover.tender.external_payment` system tender + `externalPaymentId` (the same documented mechanism add_cash_tender() already uses for COD). The eCommerce API's throwaway "Item 1" order is deleted once the real order is confirmed paid.
* Add - `record_external_card_payment()`, `get_external_payment_tender_id()`, `get_tender_id_by_label_key()` in Clover_API.
* Note - Requires the merchant to have the "External Payment" tender enabled under Clover Setup → Tenders. If missing, the order stays Open and an order note explains how to fix it (payment is still captured — nothing is lost, just not reflected as Paid in Clover until the tender is enabled and the order is reconciled manually).

2026-10-08 - version 1.0.14
* Fix - 1.0.13's duplicate-order fix never actually populated the charge-created order: the auto-created order ID was read from the wrong response field (payment.order.id, which Clover's eCommerce API does not return) instead of the documented top-level `order` string field. This silently skipped populate_ecomm_order_with_items() every time, so the Paid order kept showing the generic "Item 1" line with no note. Fixed extraction to read `order` (string) first, with defensive fallbacks, and log the raw charge response when no order id can be found so this is diagnosable from WC > Status > Logs going forward.
